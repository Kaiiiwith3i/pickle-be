# Chat and Community tabs: why they fail in Firestore mode (static diagnosis)

**Method: static code reading of the archive `../pickle-c-lb` (commit `44de87c`). Nothing here was reproduced in a browser or against the emulators; reproduction is the frontend half of tickets 06 and 07.** Each finding says what the code does and why that breaks, so treat "fails" as "expected to fail" until reproduced. Paths are relative to `../pickle-c-lb`.

## Chat tab (`src/app/(tabs)/chat.tsx`, `src/app/chat/[id].tsx`)

1. **Unread counts never exist in Firestore mode.** The inbox badge reads `chat.unreadCount` (`chat.tsx:92`, `:129`) and the tab badge sums it (`src/data/hooks.ts:322`, `:379-399`; `firestore.ts:509`). Only the local adapter computes it (`src/data/local.ts:344-347`). `FirestoreRepository.listChats` (`firestore.ts:410-420`) returns the raw thread documents, which have no such field, so every badge is 0 and the "N new" chip never shows. `docs/redevelopment-plan.md:152` already lists this as a known gap.
2. **`markChatRead` is a malformed query.** `firestore.ts:494-503` queries `where('readBy', 'not-in', [[userId]])`. `not-in` takes a list of scalar values; the nested array does not compare against the `readBy` array field the way the author meant, and `not-in` also never matches documents lacking the field. The result is that the read marker is unreliable or the query is rejected, so unread state could not clear even if it were counted.
3. **Message id is client-side time.** `sendMessage` uses `msg-${Date.now()}` (`firestore.ts:452-482`). Two messages in the same millisecond, or two users sending at once, share an id and one overwrites the other (`setDoc` without a create-only guard).
4. **Thread bookkeeping is two separate writes.** `sendMessage` writes the message and then merges `lastMessage` into the thread (`firestore.ts:~470-481`). If the second write is denied or fails, the inbox preview and ordering go stale. The rules only allow that update when `changedOnly(['lastMessage','lastMessageAt'])` (`firestore.rules:116-118`), which the code matches, so this is a consistency risk rather than a certain failure.
5. **Proposal answers are not enforced as the recipient's.** `respondToMatchProposal` (`firestore.ts:484-492`) does `setDoc(ref, { proposal: { status } }, { merge: true })`. The rule allows it only for the non-sender (`firestore.rules:126-129`), so the sender gets a raw permission error with no UI handling, and the merge replaces nothing else (court, date and label survive only because of `merge`).
6. **No access control beyond the rules.** `getOrCreateChat` (`firestore.ts:422-440`) will create a thread with any other uid, including a uid with no profile, because nothing validates the other participant. The new API returns 400 for an unknown user.

## Community tab (`src/app/(tabs)/community.tsx`)

1. **`<div>` inside a React Native screen (`community.tsx:93`).** On native (the main platform, Expo Go on iPhone) there is no `div` host component, so the screen throws on first render: the whole tab is a red-screen. It only works in the web export. Likely the single largest cause of "the tab is broken".
2. **Author can confirm their own result.** `confirmPost` allows `data.opponentId === userId || data.authorId === userId` (`firestore.ts:340-350`) and the rules let the author update every field (`firestore.rules:89-91`). A phantom win is one tap. This contradicts `docs/match-result-integrity-spec.md` section 4 and the decision in `docs/PLAN.md` (opponent or admin only).
3. **Post id is chosen by the client.** `createPost` does `setDoc(doc(db,'posts', post.id), ...)` (`firestore.ts:315-330`). Re-using an existing id overwrites someone else's post if the caller is its author, and the client can send `confirmed: true`, `verificationStatus: 'approved'`, `likedBy` or `isSample` directly because the only create rule is `authorId == auth.uid` (`firestore.rules:87-88`).
4. **Create fails when the profile id is not the auth uid.** `createPost` relies on `post.authorId` equalling `request.auth.uid`; the identity mismatch recorded as D6 in `docs/redevelopment-plan.md` (`u-local-...` ids before `saveCurrentUser` returned the stored user) makes the rule deny the write in production.
5. **Likes by non-authors rely on a field-diff rule.** `toggleLike` (`firestore.ts:~331-338`) uses `arrayUnion/arrayRemove` merges, which pass `changedOnly(['likedBy'])` (`firestore.rules:92`). That path is fine; the same rule also lets any signed-in user change `likedBy` to arbitrary content, so likes can be forged.
6. **Disputed and voided results vanish from the feed.** `isMatchBroadcastable` (`src/lib/match-verification.ts:59-64`) hides `rejected` and `expired` results from `community.tsx:78`. After an opponent disputes, the author sees their post disappear with no explanation, which reads as "broken". `getMatchVerificationStatus` (`match-verification.ts:36-60`) also auto-approves any pending result after 24 h on the client, so a result can show as approved while the stored `verificationStatus` is still `pending`; leaderboard code that reads `confirmed` and code that reads the derived status can disagree.

## What the new API does about each

Counters, ids and unread state are server-side (`/chats` computes `unreadCount`; `markChatRead` is a plain filtered batch update). Message and post ids are server-generated. Confirm is opponent-only; resolve is admin-only; `POST /posts` ignores `confirmed`, `verificationStatus`, `isSample`, `likedBy` and `authorId` from the client. The `<div>` (item 1) is a frontend fix and is not covered by the backend.

Not done: the 24-hour client-side auto-confirm (item 6) was not ported. The API stores the real state; whether to add a server-side expiry job is a product decision flagged in the report.
